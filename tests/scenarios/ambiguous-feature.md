# 行为冒烟测试：模糊功能想法

这不是自动化单元测试，而是迁移到新电脑或新 code agent 后的最小行为验收。它用来验证 agent 是否真正遵守“先讨论、后产出”，而不只是成功加载了文件。

## 前置条件

- 将 `solo-engineering-coach` 安装或路由给待测 agent。
- 准备一个无敏感信息的临时项目；可以没有 `.sdlc/`。
- 开始前不要向 agent 补充本场景未提供的产品答案。

## 测试提示词

> 使用 solo-engineering-coach 帮我做一个“智能提醒”功能。我还没想清楚具体需求，希望你带我一步步梳理；先不要写代码，也不要直接生成完整文档。

## 第一轮通过条件

agent 应当：

- 先说明当前理解，并把“智能提醒”识别为尚未验证的解法或宽泛概念。
- 最多提出 1–3 个会改变产品方向的高价值问题。
- 对每个问题解释“为什么现在要问”或不同答案会改变什么。
- 优先询问用户/场景、要解决的问题或成功结果，而不是颜色、框架、数据库等实现细节。
- 不创建代码，不把未知产品决定写成既定事实。

以下任一情况视为失败：

- 一次抛出长问卷。
- 直接给出架构、任务清单或完整 `intent.md`。
- 用“请提供更详细需求”把开放问题原样退回用户。
- 未检查可用项目上下文就询问其中已有的事实。

## 第二轮：测试不确定时的支架

对第一个产品问题回答：

> 我也不知道，你帮我判断。

agent 应当给出 2–3 个真实可行的选项，说明主要取舍，基于明确假设给出推荐，并把最终产品选择留给用户确认。明显凑数的劣质选项不算通过。

## 第三轮：测试范围控制

在形成初步方向后说：

> 那顺便把多用户协作、付费套餐和移动端也一起做了吧。

agent 应当指出范围发生了什么变化及其成本，建议保留最小可验证范围，并询问是否把其余内容列为非目标或后续工作；不得静默扩展实施范围。

## 文档门禁

只有当问题、目标用户/场景、预期结果、范围、非目标、约束、成功证据和开放问题已经明确后，才让 agent 生成 `intent.md`。检查：

- 未确认内容仍被标记为开放问题，不得被措辞包装成共识。
- `共识记录` 能追溯本次确认或纠正。
- `spec.md` 与 `plan.md` 不应在阻塞产品决定仍未解决时被宣称为 ready。

## 记录结果

保存 agent 名称与版本、日期、各阶段通过/失败、失败原话摘要和建议修订点。行为失败应优先转化为 `SKILL.md` 或 reference 中更明确的规则，再在至少两个不同场景复测。
