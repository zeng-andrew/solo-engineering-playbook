# 需求对话协议

本协议用于想法模糊、方案尚未决定或用户希望得到教学式引导的工作。它不是固定问卷；先读项目，再选择当前最能降低错误方向风险的问题。

## 1. 建立当前理解

用短段落复述你理解的目标，明确标记：

- **已知事实**：来自用户、代码、文档或可复现结果。
- **推断**：从现有证据推导、但尚未确认。
- **待决定**：不同答案会改变产品行为或工程方向的问题。

如果目标中混合了“问题”和用户预设的“解法”，把它们拆开。例如“做一个 AI 搜索框”是解法，实际问题可能是“用户找不到历史订单”。先验证问题，不默认预设解法正确。

## 2. 选择高价值问题

每轮最多问 1–3 个问题。优先级从高到低：

1. 会改变是否值得做、为谁做或成功定义的问题。
2. 会改变系统边界、数据模型、安全性或不可逆成本的问题。
3. 能排除大块错误方案空间的问题。
4. 可延后到实现阶段的偏好和细节。

每个问题附一句“为什么现在要问”，说明不同答案会改变什么。不要询问仓库里能直接查到的技术栈、命名或现有行为。

不好的问题：

> 你还有什么要求？

更好的问题：

> 这次首先服务的是偶尔使用的新用户，还是每天处理大量数据的熟练用户？这会决定我们优先降低学习成本，还是优化批量操作效率。

## 3. 用户不确定时提供支架

不要把开放问题原样退回。给出 2–3 个真实可行选项：

- 用用户能感知的语言描述结果。
- 说明主要收益、代价和后续锁定效应。
- 给出基于当前证据的推荐，并清楚标记假设。
- 如果有便宜且可逆的验证方法，优先建议试验而不是争论。

选项不应是假选择：不要把一个合理方案和两个明显糟糕方案并列来诱导答案。

## 4. 分清决策所有权

### 必须由用户确认的产品决定

- 服务谁、解决什么问题、什么算成功。
- 范围与非目标、体验取舍、价格或业务规则。
- 隐私承诺、可接受风险、不可逆数据行为。
- 会显著改变成本、时间或公开承诺的选择。

### 可由 agent 处理的工程决定

- 遵循仓库惯例的命名、文件组织和小型重构。
- 在已确认约束内的库用法、测试组织和实现细节。
- 可逆、低成本且不改变可观察产品行为的选择。

工程决定若影响公共接口、长期维护成本或未来迁移，应记录理由，并在影响重大时升级为用户决策。

## 5. 主动挑战而不夺权

发现下列情况时直接指出：

- 目标与成功指标互相冲突。
- 新需求超出已确认范围。
- 某个假设没有证据，却支撑了昂贵方案。
- “以后可能需要”正在把最小可用范围膨胀成平台建设。
- 计划缺少失败恢复、数据兼容或用户迁移路径。

采用“证据 → 影响 → 建议 → 决策权”的表达：

> 当前没有多租户需求的证据；现在引入租户隔离会扩大数据模型和测试面。我建议先保留清晰边界但不实现多租户。是否把它明确列为本次非目标？

## 6. 形成可纠正的共识

在重要转折点给出短摘要：

- 已确认的目标与边界。
- 本轮做出的决定及理由。
- 仍开放的问题，其中哪些阻塞下一步。
- 建议的下一步。

明确邀请用户纠正。只有用户确认，或用户已明确授权 agent 在该类决定上自主推进，才把状态从“提议”改为“已同意”。沉默不是产品决定的确认。

## 不同 interaction 模式

- `coach`：解释术语和因果；用例子帮助用户比较；频繁做理解校准。问题总量不必更多，但教学信息更多。
- `collaborate`：假设用户熟悉基本工程概念；直接讨论权衡和证据，仍保留关键确认。
- `fast`：压缩解释和文档长度；只问会造成返工或风险的关键问题，不跳过阻塞决策。
