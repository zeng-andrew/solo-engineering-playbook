# 交互方式与工程严谨度

`interaction` 决定怎么交流，`rigor` 决定需要多少工程证据。两者独立：专家可以用 `fast + strict` 快速沟通高风险变更；新手也可以用 `coach + light` 学习一个低风险小改动。

## Interaction

| 模式 | 适用情境 | 行为 |
|---|---|---|
| `coach` | 用户希望手把手理清需求，或领域不熟悉 | 解释为什么、提供选择与推荐、校准理解；默认 |
| `collaborate` | 用户能参与技术权衡，希望像同事结对 | 信息密度更高，少解释常识，关键决定仍确认 |
| `fast` | 目标清楚、时间敏感、用户偏好简洁 | 只保留高风险问题和短摘要，不降低必要验证 |

若未配置，先从 `coach` 开始。用户可以随时说“少解释一些”或“带我一步步想”，无需重启流程。

## Rigor

| 等级 | 默认适用 | 最低要求 |
|---|---|---|
| `light` | 局部、可逆、影响面小，现有测试能覆盖 | 简短 intent/plan，可合并 spec；运行针对性验证 |
| `standard` | 普通功能、缺陷修复、跨文件重构 | 独立 intent/spec/plan/verification；验收标准可追踪 |
| `strict` | 身份权限、支付、敏感数据、破坏性迁移、合规、公共 API、生产基础设施 | 决策与回滚显式；关键门禁获确认；含失败路径、兼容/迁移和更强证据 |

`rigor` 不直接决定提交数量。项目另用 `git_checkpoints` 控制 Git 检查点；默认 `strict-only`，即 strict 工作项形成门禁和实现增量提交，light/standard 不被机械拆分。具体规则见 [Git 检查点](git-checkpoints.md)。

## 风险评估

从以下维度判断，任何一项高风险都足以建议 `strict`：

- **影响范围**：单一内部路径，还是大量用户/系统。
- **可逆性**：能否立即回滚，是否会永久改变或删除数据。
- **可检测性**：失败能否在测试或监控中及时发现。
- **安全与隐私**：是否改变权限边界、秘密、个人或敏感数据处理。
- **金钱与承诺**：是否触发付费、计费、合同、通知或公开 API 承诺。
- **不确定性**：需求、依赖或现有行为是否缺乏证据。
- **耦合**：是否跨服务、跨团队、跨版本或需要用户迁移。

推荐格式：

> 建议 `rigor: strict`。原因不是代码量，而是这次会迁移不可恢复的用户数据，失败不容易立即发现。最低需要迁移前备份、干跑、兼容窗口和回滚验证。

## 变更规则

- 风险上升时立即建议升级 rigor，并说明新增成本和能降低的具体风险。
- 发现任务比预想更局部时可以建议降级，但保留已有的有价值证据。
- 用户可以接受风险并选择较低等级，但应记录被接受的具体风险；安全、权限或不可逆外部动作仍需遵守授权边界。
- 文档数量不是严谨度本身。证据可追踪、失败可恢复、关键决定明确才是目标。
